How RescueLINK talks when the network is gone

Responders from several agencies need voice, text, images and position in the first 4.5–5 hours after a disaster — exactly when cellular and radio infrastructure is destroyed or not yet restored. This is the complete reference for the communication system: the four transport tiers, why each technology beat its alternatives, packet formats, failure modes, and what is still unresolved.

01The core requirement

Responders from multiple agencies must communicate — voice, text, images, position — in the first 4.5–5 hours after a disaster, when cellular and radio infrastructure is destroyed or not yet re-established. Six constraints shaped everything that follows.

No master / slave

A leaderless network was a hard requirement. If one device drops, the network must not collapse.

Android only

iOS is explicitly out of scope: Wi-Fi Aware behaves differently there, and cross-platform would mean two implementations.

No rooting or jailbreaking

Stock, unmodified Android devices only.

Multi-hop is mandatory

Direct-range-only communication was rejected as insufficient.

Walkie-talkie replacement, plus more

Must do what radios do (voice, PTT) and what they cannot (text, images, GPS).

Battery optimisation not required

The 4.5–5 hour scope fits stock phone battery life; no duty-cycling engineering needed.

02Technology selection — what was chosen and what was rejected

Rejected
Wi-Fi Direct

Fundamentally master/slave. One device must be Group Owner — the central coordinator broadcasting beacons and managing connections; the rest are clients. A mesh on top needs every device to play both roles at once (client to one group, GO to another). If the GO drops out, the local cluster collapses until a new election completes. That directly violates the leaderless requirement.

Rejected · was initially recommended
Meshrabiya (UstadMobile)

Real, maintained, and genuinely the lowest-effort path to multi-hop on Android: a custom SocketFactory gives ordinary TCP/UDP sockets, 300 Mbps+ throughput and virtual link-local routing (169.254.x.y) with BATMAN-style forwarding. Rejected for two reasons:

1. It is not actually leaderless. Under the virtual IP layer it automates the AP + Station hack — A starts a hotspot, B connects then starts its own, C connects to B. That gives rigid tree/chain topologies, not flat meshes; if an intermediate parent walks away, everything downstream is cut until it re-links. Claiming "leaderless" on top of this would not survive a technical question.

2. It needs out-of-band priming. Nodes cannot discover each other over the air; SSID, passphrase and IPv6 link-local address are passed by QR code or BLE first. Expecting responders from different agencies to scan each other's QR codes mid-crisis is not a realistic assumption.

Rejected
Wi-Fi Ad-Hoc (IBSS)

Classic flat topology, genuinely decentralised — but locked down at OS/firmware level on modern Android and iOS for security and power reasons. Requires rooting. Out of scope.

Control channel only
BLE Mesh

The most mature strictly-leaderless option on consumer phones: managed flooding, zero hierarchy, no pairing. But bandwidth is far too low for voice and images. Viable as a discovery/control channel, not as the primary data transport.

Chosen

Wi-Fi Aware (Neighbor Awareness Networking) — Android 8.0+ / API 26, android.net.wifi.aware. The modern official Wi-Fi standard purpose-built for leaderless localised clusters.

  • Symmetrical discovery. Devices form a cluster by synchronising Wi-Fi clocks and exchanging beacons in shared discovery windows. No access point, no group owner, no master.
  • Publish / subscribe. Node A publishes a service name; Node B subscribes to it. There is no central identity to connect to.
  • On-demand data paths (NDP). When data needs to move, two devices spin up a temporary direct link that tears down after transmission.
  • Automatic discovery. No QR/BLE priming — unlike Meshrabiya.

The trade-off accepted: Wi-Fi Aware gives raw point-to-point data paths only. All multi-hop routing must be written by the team. It is the single largest piece of custom engineering in the project and sits outside the team's core AI/ML–web–GIS skill set. It was chosen deliberately: a defensible leaderless claim was judged worth the extra work.

Known constraint — hardware fragmentation. Wi-Fi Aware needs manufacturer antenna/firmware support, not just Android 8+. Common on flagship and mid-range chipsets (Snapdragon, Tensor); frequently stripped from ultra-budget handsets. Target devices must be verified before the demo.

03Tier 1 — local cluster mesh (phone to phone)

Connection layer

Wi-Fi Aware lifecycle:

System check→Attach session→Publish / Subscribe→Peer discovery→Open data path (NDP)

Manifest permissions: android.hardware.wifi.aware (uses-feature), ACCESS_WIFI_STATE, CHANGE_WIFI_STATE, ACCESS_FINE_LOCATION (required for P2P discovery).

Availability check before initialising a node:

val wifiAwareManager = context.getSystemService(Context.WIFI_AWARE_SERVICE) as WifiAwareManager?
val isSupported = context.packageManager.hasSystemFeature(PackageManager.FEATURE_WIFI_AWARE)
if (isSupported && wifiAwareManager?.isAvailable == true) { /* initialise node */ }

Data path setup: use WifiAwareNetworkSpecifier with a PSK passphrase, request via ConnectivityManager with TRANSPORT_WIFI_AWARE, then obtain a socket from network.getSocketFactory().

Critical implementation note

Bind each socket to its returned peer Network object. Do not assume ordinary routing will select the intended NAN interface.

Range: ~100–200 m per hop, heavily dependent on obstructions.

Routing layer — custom, and the core engineering work

Every packet is wrapped:

data class MeshPacket(
    val packetId: String,     // UUID — prevents infinite loops
    val sourceNodeId: String, // original sender
    val destNodeId: String,   // ultimate target (or broadcast)
    val hopLimit: Int,        // TTL — prevents packet storms
    val payload: ByteArray    // encrypted body
)

Managed flooding (gossip) — the chosen routing strategy

Rather than computing a single route, send the same packet down every available path and let the fastest win. The first copy to arrive is processed; every duplicate arriving later is dropped by the dedup cache.

class AudioPacketReceiver {
    private val seenPackets = LinkedHashSet<String>()  // rolling cache of ~50

    fun onPacketReceived(packet: MeshPacket) {
        if (seenPackets.contains(packet.packetId)) return  // duplicate — drop
        seenPackets.add(packet.packetId)
        if (seenPackets.size > 50) seenPackets.remove(seenPackets.iterator().next())
        codec2Decoder.play(packet.payload)
    }
}

Why flooding beats computed routes here: lowest possible latency (no route computation delay), and seamless resilience — if one node steps behind a wall, voice continues through the alternate path with zero switch-over delay or audio cut.

Concurrency limit — a real constraint

Most Android Wi-Fi Aware chips sustain only 4–6 concurrent active data paths. If a relay node is at capacity but must forward to a new peer, the routing service has to tear down an idle path, establish the new one, push the queue and close it (intermittent routing).

Hop limits: start qualification at three Wi-Fi voice hops and three LoRa forwarding hops.

Multi-path splitting — explicitly rejected

Splitting one stream across several simultaneous routes was considered and rejected for both voice and images.

For voice

Codec 2 packets are 20–50 bytes — far too small for any serialisation benefit on links handling megabits per second. Worse, different routes have different hop counts and latencies, causing severe out-of-order delivery. Fixing that needs a much larger jitter buffer, which increases latency and makes conversation laggy. Real-time speech cannot tolerate this.

For images

The bottleneck is not bandwidth but the 4–6 concurrent-connection cap. Routing chunks down multiple paths forces intermediate nodes to hold multiple NDPs at once, locking up the whole network's routing capacity for one transfer and draining batteries.

Correct pattern instead: managed flooding for voice (same packet, all paths, first wins); single best path with chunking for images.

04Voice — push-to-talk with Codec 2

Why Codec 2

Codec 2 compresses speech to 450–3200 bps using sinusoidal coding specialised for the human voice. At 1200 bps, one second of audio is about 150 bytes. That makes voice packets small enough to route across multiple hops with virtually no congestion, and resilient — even a degraded link passes them without stuttering.

Baseline selected: 1600 bit/s — 320 samples at 8 kHz = 40 ms of audio → 64 bits (8 bytes). A 1300 bps mode exists; select it by intelligibility testing, not by assumption.

Skill gap

Codec 2 is C. It has to be included as a source tree and compiled through Android Studio's CMake/NDK support, with a JNI wrapper passing raw PCM down and receiving compressed bytes back. For a team without embedded/systems experience this is a genuine gap and needs a named owner.

At one packet per 80 ms: 128 × 8 / 0.08 = 12.8 kbit/s. So 1.6 kbit/s of speech encoding costs about 12.8 kbit/s at the IP layer — before Wi-Fi overhead, redundancy or extra forwarding hops.

Media policies

  • Jitter buffer: start around 120 ms, adapt within ~80–240 ms. Mandatory — packets hopping dynamically will not arrive evenly spaced, and playing them on arrival sounds broken and robotic.
  • Discard packets arriving after the playout deadline; never retransmit late voice.
  • Expire voice after ~500 ms in transit.
  • Conceal isolated losses with attenuation; move to comfort noise for sustained loss. Codec 2 does not supply a complete packet-loss strategy — the receiver must implement concealment.
  • Optional: include one previous Codec 2 frame for loss recovery.
  • Avoid mixing multiple simultaneous talkers into one channel.

Half-duplex PTT

Wi-Fi antennas cannot transmit and receive on the same frequency at the same time, so strict PTT is architecturally required, not a UX choice.

Pressed

Stop listening, open the mic, encode, broadcast.

Released

Close the mic immediately; keep audio output open for inbound packets.

  • VAD. If the user holds PTT but stops speaking, detect silence and pause transmission — protects the network and the battery.
  • Floor control. A temporary floor controller grants short, renewable speaking leases. Emergency traffic can pre-empt routine traffic. Partitioned groups operate independently; on reconnection, finish or terminate existing talkspurts before adopting one floor epoch.
  • Targeted PTT. Selecting a specific node needs no new networking — it uses the existing destNodeId unicast addressing. Only the target plays audio; everyone else relays. Group PTT forwards over a bounded distribution tree: "broadcast" is application-level replication, not native multi-hop multicast.

05Images and data transfer

Images have the inverted requirement: 100 % integrity, latency tolerant. Voice is the opposite.

CompressChunkSequence headersMesh transportReassemble & verify
  1. Never send raw bitmaps — compress to WebP (or JPEG) first: bitmap.compress(Bitmap.CompressFormat.WEBP, 75, stream)
  2. Chunk to ~1 KB — below the typical 1500-byte MTU, so the OS never fragments unpredictably. For Wi-Fi UDP use a conservative 1,200-byte application datagram ceiling.
  3. Wrap every chunk: 
    data class ImageChunkPacket(
    val imageId: String,   // unique per transfer
    val totalChunks: Int,
    val chunkIndex: Int,
    val data: ByteArray    // 1 KB slice
)
  4. Transport choice:
    • Hop-by-hop TCP (recommended): each hop transfers reliably; the intermediate node caches fully, then forwards. Needs storage at relays.
    • UDP + ARQ: blast chunks; the receiver requests missing indices with small control packets. Faster, less relay memory.
  5. Checkpointed resume: if a relay walks away mid-transfer, the sender saves its chunkIndex, waits for an alternate path, asks the receiver for its last verified chunk, and resumes — never from zero.

06Tier 2 — inter-cluster bridge (ESP32 + LoRa)

The hard constraint

An ESP32 cannot join a Wi-Fi Aware cluster. NAN lives in the Android Wi-Fi driver/firmware stack; Espressif's ESP-IDF does not expose it at all. Espressif's own ESP-WIFI-MESH is proprietary and phones cannot join that either. The ESP32 can only ever be a separate bridge/gateway node, attached to a phone by:

  • Classic Wi-Fi AP — a "cluster lead" phone connects like a normal hotspot (simplest, most reliable)
  • BLE (GATT) — lower throughput, better battery, better for unattended multi-hour gateway operation

Firmware: Meshtastic, not custom

Meshtastic (open-source ESP32 + LoRa firmware, actively maintained) ships almost exactly what is needed: multi-hop LoRa mesh with managed flooding, GPS position sharing, text messaging, PSK/PKI channel encryption, and a community UDP bridge component that exposes the LoRa mesh over UDP — the integration point for the phone and backend. This turns the whole LoRa backbone from "write embedded mesh routing from scratch" into "deploy proven firmware and write a thin adapter".

Payload constraint

Text, GPS and status codes only — no images, no voice. LoRa runs 0.3–27 kbps depending on spreading factor; even Codec 2's lowest mode plus LoRa overhead and duty-cycle limits makes usable voice unworkable. Standard SX126x operation caps a packet at 255 bytes; use 240 bytes as the normal application limit for headroom.

Airtime — the real capacity limit

LoRa must be managed in airtime, not packet count. At 125 kHz bandwidth, CR 4/5, explicit header, 8-symbol preamble:

PacketSF7SF9SF12
164-byte telemetry0.266 s0.841 s6.070 s
176-byte SOS0.282 s0.902 s6.562 s
240-byte maximum0.379 s1.189 s8.528 s

Under a 1 % airtime allowance (36 transmit-seconds per hour) a transmitter could send only about 42 telemetry packets an hour at SF9 before reserving capacity for anything else. Therefore:

  • Keep frequent individual position updates inside Wi-Fi clusters.
  • Backhaul only selected changes and compact cluster summaries — labelled as summaries, with gateway provenance; retain the original signed observations for later sync.
  • Use SF7/SF9 where link quality permits; treat SF12 as a low-capacity contingency.
  • Suspend routine telemetry when critical queues grow.
  • Prefer routes through designated repeaters. Routine telemetry must not flood every repeater; bounded duplicate forwarding with randomised suppression is for SOS only.
Regulatory

India's WPC de-licensed band is 865–867 MHz, with duty-cycle restrictions that must be confirmed before setting message intervals. Frequency, EIRP, duty cycle, dwell time and channel access all follow the deployment jurisdiction. Use raw LoRa, not LoRaWAN — LoRaWAN assumes a gateway/network-server architecture that does not fit this peer/repeater topology.

The ESP32's two distinct roles

Role 1
Dropped relay node

Placed between two phones too far apart, extending reach within a cluster's path to command.

Role 2
Cluster bridge

Connecting two separate mesh clusters to each other. Same hardware, different purpose — keep them separate in write-ups.

Gateway fail-over

Because the ESP32 holds the physical LoRa link, the peripheral controls fail-over, not an election — a replacement phone must be physically connected by USB or within BLE range.

  1. Provision at least two authorised gateway-capable phones per cluster.
  2. The ESP32 keeps a single active attachment leasewith a monotonically increasing generation number.
  3. The active phone heartbeatsinitially every 2 s.
  4. On lease expiry, candidates authenticate and request ownership.
  5. The ESP32 selectson external power, remaining battery, cluster reachability, then a deterministic tie-break.
  6. The new phone exchanges queue inventoriesand resumes delivery with the existing message IDs.

Keep queued records on the ESP32 and on the originating phones. Lease generations fence out the old phone if it reconnects.

07Tier 3 — satellite link

Reference hardware: Iridium Short Burst Data, e.g. RockBLOCK 9603 (~$250–300 plus ~$15/month), simple UART interface. Payload: about 340 bytes mobile-originated, about 270 bytes mobile-terminated — coordinates and short instructions only.

Important correction

Satellite is not range-limited like LoRa. Iridium is low-orbit with near-global coverage; the real constraint is sky visibility — not blocked by buildings, canopy or being indoors. So the modem attaches to specific gateway nodes (likely 1–2 in total, cost-driven) and other clusters route to it over the LoRa backbone.

Simulated for the hackathon. Build the real interface — the same message format and size cap a RockBLOCK exposes — and swap only the transport: route through the project's own backend, inject realistic latency (seconds to low minutes), enforce the 340-byte cap. Pitch framing: "transport is simulated; gateway firmware is written against the same interface real hardware exposes — a drop-in swap, not a redesign."

Why it was kept when cutting it was proposed. The argument for removal was that there is "always" a link to command. That fails precisely where this platform matters most — remote Western Ghats landslides, wide flood districts where command may be 50–200 km away through LoRa-degrading terrain, with no time to deploy a repeater chain mid-golden-hour. Since it is simulated anyway, keeping it costs nothing on build day but preserves coverage for the worst cases.

Correct framing: LoRa is the default path; satellite is the fall-back for out-of-range command centres — not an always-on requirement.

08Tier 4 — adaptive online transition

Not a separate system — an extension of Tier 1 routing with "cloud" added as a possible destination. The named pattern is Delay/Disruption-Tolerant Networking (DTN): a real discipline (NASA deep-space comms, the IETF Bundle Protocol), worth citing.

  1. Connectivity checkConnectivityManager + NET_CAPABILITY_VALIDATED — detects real internet, not just an active radio.
  2. Transport priority ladder, per messageDirect internet/cellular → mesh peer with internet → local mesh → LoRa backbone → satellite (short emergency only).
  3. Gateway auto-promotionAny phone that regains internet broadcasts a small "I have internet" beacon into the mesh; peers' routing tables send cloud-bound traffic through it. Same next-hop logic, no new protocol. Works in both directions — it also carries inbound alerts into a dead zone.
  4. Reconciliation syncOn reconnect, flush queued reports, images and the GPS trail in one batch.
Key property

The mesh is never torn down when internet returns — it stays live underneath as a resilience layer. A responder walking into a dead zone twenty minutes later does not drop off the map; they fall one rung down the same ladder automatically. The network has a quality gradient, not an on/off state.

When cellular is available

Traffic routes through the cloud backend directly, and PTT shifts to a cloud-relayed voice channel: client → own server → client(s). This is simpler than mesh PTT, not harder:

  • Same Codec 2 pipeline — only the destination changes.
  • No WebRTC / STUN / TURN. The server has a public address, so both clients connect to it — client-server, not peer-to-peer NAT traversal.
  • Floor control becomes trivial — one server-side flag instead of distributed agreement across peers.
  • It is an upgrade. On the mesh two responders need a physical hop-chain between them; over cellular any two responders can talk regardless of distance.
Build sequencing tip

Build and test cloud PTT first, over ordinary Wi-Fi with a laptop as the server, before touching Wi-Fi Aware. It de-risks the audio pipeline early and produces a demoable voice feature fast.

09Alert delivery into a dead zone

Sensor data reaching the backend is usually not blocked by local damage — IMD, GSI and CWC report over their own national telemetry networks, not local cell towers. The real bottleneck is the backend reaching responders already inside a dead zone.

Three paths, no new subsystem:

Most realistic
Patchy infrastructure

Disasters rarely kill connectivity uniformly. The alert reaches whichever device still has signal; that device auto-promotes to gateway (Tier 4 logic running inbound) and floods the alert into the mesh.

Total local blackout

The alert is injected at the LoRa/satellite tier from outside the dead zone and floods down through the same managed-flooding relay.

Pre-loaded static risk

Baseline risk classification is known before deployment, so cache it on devices at mission briefing — a responder entering a known High-risk zone has that context even in a worst-case blackout.

One addition required

The packet design is unicast-oriented (destNodeId). Alerts need a broadcast message type — the same TTL/dedup/flood logic, but every node treats itself as the recipient.

10Range — the honest picture

Radio power cannot be boosted on stock phones. "Range extension" is not a software feature. The real levers:

Hop density

More responders spread out, each relaying, extends coverage. Per-hop range stays ~100–200 m.

Elevation

Line of sight dominates. A phone or gateway on a vehicle roof or high ground dramatically increases reach.

ESP32 relay drops

Physically placing a node in a gap too wide for two phones.

Build mesh topology visualisation instead of claiming range boosting. A live view of discovered vs. connected peers, link quality, route hops, gateways and partition boundaries lets a coordinator say "move to that ridge" to bridge a gap. It is a real operational tool and a strong demo moment — the mesh healing itself. (This is what the command console does.)

Do not

Infer peer signal strength from the phone's unrelated infrastructure-network RSSI. Where direct peer measurement is not available, show a clearly labelled delivery-quality estimate, not a fake signal bar.

Repeater antenna placement: above obstructions. Non-line-of-sight range must be measured, not assumed from open-field specifications.

12Security on the mesh

  • Wi-Fi Aware tier: AES-256 at the packet layer; keys provisioned during mission briefing, not negotiated live.
  • LoRa tier: Meshtastic's built-in PSK/PKI channel encryption — free, no extra work.
  • Backend / satellite: standard TLS in transit, encryption at rest.
  • Authentication without connectivity: identity provisioned before deployment (QR / pre-registration), never requiring a live login — mandatory given the zero-connectivity premise.
Provisioning as a feature, not a weakness

"Devices are provisioned during mission briefing, so only authorised multi-agency responder devices join the network." Better than open-join, which is a genuine security concern for a tactical network.

Nonce discipline: derive keys by incident, sender, audience and key epoch; construct the nonce from boot epoch and sequence. Persist epoch advancement before sending — never reuse a nonce after a reset, reinstall or counter roll-over.

15Demo strategy

Live mesh demos are notoriously flaky on stage — RF interference from hundreds of competing devices at a hackathon venue is a real, common problem.

  • Always have a pre-recorded backup video of the multi-device relay working. Standard practice, not a red flag to judges.
  • Lead with the mesh topology visualisation — it makes the invisible visible and shows self-healing.
  • Build cloud PTT first so a working voice feature exists early, independent of mesh reliability.
  • Be honest about what is simulated (satellite). Staged honesty scores better than unverifiable claims.
